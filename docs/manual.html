Neovim configuration manual

Dark 2026 for Neovim

VS Code's Dark 2026 theme, ported to Neovim by generating the colourscheme from the theme JSON rather than matching it by eye — with basedpyright, Ruff, a debugger and a file tree wired to the keys you already use.

$ git clone https://github.com/xmandeng/nvim-vscode-2026.git && cd nvim-vscode-2026 && ./bootstrap.sh

Install

bootstrap.sh backs up any existing ~/.config/nvim, links this one in, then installs plugins, language servers and treesitter parsers. Nothing is deleted.

How the colour port works

The goal is that Neovim shows the same hex values VS Code shows. Three things make that harder than copying a palette.

1. The theme is an inheritance chain

2026-dark.json is not a full theme. It carries an include that resolves through three ancestors: 

dark_vs.json → dark_plus.json → dark_modern.json → 2026-dark.json

Flattening that chain yields 329 UI colours and 118 token rules. Parent tokenColors are concatenated ahead of the child's, which matters next.

2. Dark 2026 is a hybrid, and naive matching gets it wrong

Dark 2026 layers a GitHub-Dark-style palette over the classic Dark+ base. The Dark+ colours still show through wherever Dark+ has a more specific selector. So in one Python file, from one theme, import is pink and def is red:

Token scope keyword.control.import.python
× keyword 1 segment — less specific #FF7B72
× markup.heading entity.name descendant — needs a heading ancestor #79C0FF
✓ keyword.control 2 segments — most specific direct match #C586C0

Resolving "last rule wins" would paint everything with the GitHub palette. The generator implements TextMate's real ranking, (direct, specificity, order):

Rank keyRule
directA descendant selector such as markup.heading entity.name only applies inside a heading. Bare scopes are resolved with no ancestor stack, so descendant selectors rank below direct ones. Without this, every entity.name.* token is hijacked and decorators come out blue instead of orange.
specificityMore dot-segments wins, so keyword.control beats keyword.
orderLater files in the include chain win genuine ties.

3. Semantic tokens, not just treesitter

VS Code colours Python mainly from Pylance's semantic tokens, not the grammar. Neovim has the same mechanism: a server supporting textDocument/semanticTokens drives the @lsp.type.* groups. The generator encodes VS Code's built-in semantic-token-to-scope defaults — class → entity.name.type.class, parameter → variable.parameter — plus modifier transforms such as *.defaultLibrary → support.*, then resolves each through the same engine.

Neovim appends the filetype, producing @lsp.type.class.python, which falls back through the standard @a.b.c → @a.b → @a hierarchy.

Alpha

VS Code themes use 8-digit #RRGGBBAA colours — editor.selectionBackground is #276782dd. Terminals have no alpha channel, and handing an 8-digit value to nvim_set_hl raises "Invalid highlight color" and aborts the colourscheme mid-load, leaving Normal unset. Every such colour is composited over its real backdrop at generation time: #276782dd over #121314 becomes #245C73.

A validator runs before emission and refuses to write anything that is not #RRGGBB, so that class of bug cannot reach the editor. The loader also sets each group independently, so a bad personal override degrades to one warning instead of an unstyled editor.

Terminal & tmux

The editor background is #121314. On a terminal set to a different dark background, panels and splits will not line up with the editor — so the repo ships generated schemes for five hosts in terminal/.

HostHow to apply
Alacrittygeneral.import = ["~/.config/alacritty/vscode-2026-dark.toml"]
Kittyinclude vscode-2026-dark.conf
Ghosttytheme = vscode-2026-dark
WezTermcolors = require("vscode-2026-dark")
tmuxsource-file ~/.config/tmux/vscode-2026-dark.conf

Terminal opacity breaks exactness. A translucent window composites #121314 against whatever is behind it, so the editor background is no longer the value the theme specifies. Set opacity to 1.0 if you want the colours to be literally correct.

Under tmux, true colour must survive the pane. tmux 3.2+ usually detects it, but if colours look flattened, force it: 

set -g default-terminal "tmux-256color"
set -ga terminal-overrides ",*256col*:Tc"

Keybindings

VS Code chords are mapped wherever a terminal can express them and they do not hide a core Vim key (CtrlW, CtrlA, CtrlZ, CtrlY, CtrlN, CtrlB, CtrlT, gi and gr keep their Vim meaning). Every one also has a Space leader equivalent that works anywhere — press Space in normal mode to browse them.

Read this before blaming a binding. Terminals traditionally encode CtrlShiftX identically to CtrlX. Telling them apart needs the kitty keyboard protocol.

Kitty Ghostty WezTerm Alacritty 0.13+ Terminal.app older xterm

Without it, the CtrlShift rows below do nothing. Use the leader alternative instead. Ctrl/ is the other casualty — most terminals send Ctrl_, which is mapped alongside it.

Python

Two servers, matching the split you already run in VS Code.

basedpyright

Types, hovers, completion, inlay hints, and the semantic tokens that drive the syntax colours. An open-source fork of Pyright with the richness Pylance provides — Pylance itself is closed and cannot run outside VS Code.

ruff

Lint, format, and organise imports — the same engine as your charliermarsh.ruff extension, reading the same pyproject.toml.

Settings worth knowing

SettingValue hereWhy
typeCheckingModestandardbasedpyright's own default is recommended, far stricter than Pylance. standard reproduces what VS Code shows you today.
diagnosticModeopenFilesOnlyMatches VS Code. Set to workspace for project-wide errors.
disableOrganizeImportstrueRuff owns import order; stops the two servers fighting.
hoverProvider (ruff)offbasedpyright's hovers are better; avoids duplicates.

Format on save

Runs ruff_organize_imports, then ruff_format. Ruff's fixes (ruff_fix) are left out on purpose: they delete an import you have just typed but not used yet. Apply them as code actions instead. Toggle it without editing config: 

:FormatDisable      " globally
:FormatDisable!     " this buffer only
:FormatEnable

Some overlap between the two servers is expected — both flag undefined names, exactly as the two extensions do in VS Code.

The panel opens on session start with Scopes, Watches, Stack Frames and Breakpoints on the left, REPL and console at the bottom; the status bar turns orange while stopped. Variable values appear inline as virtual text at end of line.

The interpreter split that trips everyone up. The adapter interpreter must have debugpy importable — this config uses Mason's dedicated venv. The debuggee interpreter is chosen separately per configuration via pythonPath, preferring $VIRTUAL_ENV, then $CONDA_PREFIX, then .venv/, venv/, env/ in the project root.

Pointing the adapter at a project venv without debugpy is what produces adapter python exited with 1.

Customising

lua/vscode2026/generated.lua is generated and will be overwritten. Personal changes belong in the overrides table, which is applied on top and survives regeneration. 

require('vscode2026').setup({
  transparent     = false,   -- drop the editor background
  italic_comments = true,
  overrides = {
    Comment                 = { fg = '#7A8188', italic = false },
    ['@lsp.type.parameter'] = { fg = '#9CDCFE' },
    CursorLine              = { bg = '#1B1D1F' },
  },
})

The palette is available if you would rather build on it than hard-code hex:

local p = require('vscode2026').palette()
-- p.bg, p.fg, p.accent, p.error, p.git_add, p.ansi.blue, ...

Adding a language server

Add it to ensure_installed in lua/plugins/lsp.lua; anything listed is enabled automatically. Because colours come from semantic tokens and treesitter captures rather than per-language rules, a new language picks up Dark 2026 with no theme work.

Adding plugins

Drop a file into lua/plugins/. Everything there is imported automatically — no registration step.

Auto-save

There is none, on purpose. Saving runs format-on-save, so a timer that saves for you would also reformat the file while you are still typing it.

Regenerating

When VS Code updates its theme, re-read it rather than chasing diffs by hand.

CommandEffect
make themeRe-read the VS Code theme JSON on this machine and rewrite generated.lua.
make terminalRewrite the five terminal emulator palettes from that output.
make checkParse-check every Lua file.
makeTheme and terminal together.

The generator is not specific to Dark 2026 — point it at any VS Code theme, including one from a marketplace extension in ~/.vscode/extensions/<publisher>.<name>/themes/: 

$ make theme THEME=/path/to/some-theme.json

Troubleshooting

Colours look washed out

The terminal is not in true colour. :lua print(vim.o.termguicolors) must report true, and $COLORTERM should be truecolor. Over SSH, TERM must survive the hop.

One token is the wrong colour

Put the cursor on it and run :Inspect — that reports the treesitter capture, the LSP semantic token, and the group actually winning. Compare against VS Code's Developer: Inspect Editor Tokens and Scopes. Same scope but different colour is a port bug; different scopes means the parser differs, not the theme.

Boxes or blanks instead of icons

The terminal font is not a Nerd Font — Neovim cannot fix that from inside. Confirm the codepoints survived with :lua print(vim.inspect(require('config.icons').diagnostics)); any value printing as "" means the file was corrupted in transit.

Icons are defined by codepoint through nr2char() rather than as literal glyphs, precisely because those glyphs live in the Unicode Private Use Area and are routinely stripped by copy/paste, shell heredocs and some editors. The config targets Nerd Fonts v3.

No Python diagnostics or completion

Check :LspInfo, then :Mason. basedpyright needs Node.js and will fail to install without it. If your own package imports are unresolved, activate the venv before launching, or add a pyrightconfig.json: 

{ "venvPath": ".", "venv": ".venv", "extraPaths": ["src"] }

Something broke after an update

lazy-lock.json pins all 33 plugins to known-good commits — that file is what makes an install reproducible across hosts. 

$ git checkout lazy-lock.json
$ nvim --headless "+Lazy! restore" +qa

Reverting entirely

bootstrap.sh never deletes: your previous config is at ~/.config/nvim.backup.<timestamp>. Swap it back and clear the state directories.
